# TB4 — Сервис авторизации по номеру телефона и реферальная система

Учебный дипломный проект на **Python 3.13, Django 5.2 LTS, Django REST Framework, PostgreSQL и Docker**. Предусмотрены API, веб-интерфейс Django Templates, ReDoc, Postman-коллекция, миграция БД, тесты pytest и покрытие `pytest-cov`.

> **Внимание:** SMS в этой версии **не отправляются** настоящим абонентам. Четырёхзначный код выводится в журнал процесса Django; реализация предназначена для локальной демонстрации. Для публичного развёртывания требуется подключить реального SMS-провайдера и дополнительную защиту на периметре. `DEBUG=0` **запрещает** использование демонстрационного SMS-бэкенда.

## 1. Возможности

- Два этапа входа: запрос OTP по телефону → подтверждение четырьмя цифрами.
- Задержка при имитации отправки **1.5 с** (настраивается); код действителен **5 минут**.
- Защита OTP: максимум **5 попыток**, повторный запрос не чаще раза в **60 секунд**, предыдущий код автоматически заменяется новым; одноразовое использование.
- Автоматическая регистрация нового пользователя только после правильного OTP.
- Уникальный **шестисимвольный** буквенно-цифровой код каждого пользователя.
- Активация чужого кода только **один раз**. Запрет собственного кода и циклов приглашений.
- Профиль с активированным кодом и списком телефонов приглашённых.
- API-токен `Authorization: Token <token>` и завершение API-сессии.
- Минимальный шаблонный веб-интерфейс на `/` и `/profile/` с защитой CSRF.
- Документация OpenAPI, ReDoc и Swagger UI; коллекция Postman.

## 2. Быстрый запуск на Ubuntu 26.04 + VS Code

Установите Docker Engine + Docker Compose Plugin. В терминале VS Code:

```bash
cp .env.example .env
# Для безопасного локального секрета выполните:
python3 -c 'import secrets; print(secrets.token_urlsafe(48))'
# Вставьте результат как DJANGO_SECRET_KEY в .env

docker compose up --build -d
docker compose logs -f web
```

После запуска:

| Адрес | Назначение |
|---|---|
| http://localhost:8000/ | Вход по телефону |
| http://localhost:8000/verify/ | Подтверждение кода |
| http://localhost:8000/profile/ | Профиль и реферальный код |
| http://localhost:8000/api/redoc/ | ReDoc |
| http://localhost:8000/api/swagger/ | Swagger UI |
| http://localhost:8000/api/schema/ | OpenAPI-схема |

**Где взять демонстрационный OTP:** после POST `/api/auth/request-code/` либо после ввода телефона в браузере появится запись в логах сервера:

```text
[DEMO SMS / НЕ ДЛЯ PRODUCTION] Номер: +79991234567; код: 1234
```

Это **пример формата сообщения**, а не фиксированный код: OTP каждый раз генерируется случайно, в диапазоне от 0000 до 9999. `docker compose logs --tail=40 web` покажет последние сообщения.

Остановить: `docker compose down`. Для полного **удаления локальных данных**: `docker compose down -v`.

> Сервис веб-приложения доступен только с хоста `127.0.0.1:8000`. Для удалённого доступа необходим отдельно настроенный HTTPS reverse proxy и реальный SMS-провайдер.

## 3. Запуск локально без Docker

Нужен Python 3.10–3.13 и установленный PostgreSQL. Установка зависимостей:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
```

В `.env.example` приведены переменные окружения; Django **не считывает `.env` автоматически** вне Docker Compose. Для локального запуска можно экспортировать их в shell:

```bash
export DEBUG=1
export DJANGO_SECRET_KEY='local-only-secret-change-me'
export POSTGRES_DB=tb4 POSTGRES_USER=tb4 POSTGRES_PASSWORD='your-password'
export POSTGRES_HOST=localhost POSTGRES_PORT=5432
python manage.py migrate
python manage.py runserver
```

Для быстрого **локального ознакомления без PostgreSQL** допустимо `export USE_SQLITE=1` перед `migrate`, после чего работает SQLite. **Для сдачи диплома используй PostgreSQL через Docker Compose.**

## 4. REST API

Телефон **только в международном формате**, например `+79991234567` (8–15 цифр после `+`, первая не `0`). Запросы и ответы JSON. Публичное API не возвращает OTP.

### Запрос кода

```http
POST /api/auth/request-code/
Content-Type: application/json

{"phone_number":"+79991234567"}
```

Ответ `202 Accepted`:

```json
{"detail":"Демонстрационный код отправлен (смотрите журнал сервера).","expires_in":300}
```

Ошибка `400` при неверном формате. Ошибка `429` при повторном запросе ранее 60 секунд: `{"detail":"Повторный код можно запросить через 60 сек."}` и HTTP-заголовок `Retry-After`. Отдельно действует IP-based throttling `10/hour` (для одного процесса, в демонстрационной конфигурации).

### Подтверждение кода

```http
POST /api/auth/verify-code/
Content-Type: application/json

{"phone_number":"+79991234567","code":"1234"}
```

Пример ответа `200 OK` (значения условные):

```json
{
  "token":"f67d...",
  "token_type":"Token",
  "created":true,
  "profile":{
    "phone_number":"+79991234567",
    "invite_code":"X2K9BZ",
    "activated_invite_code":null,
    "invited_phones":[]
  }
}
```

`created: true` при первом успешном входе, `false` при повторной авторизации. Ошибка `400` при неверном/истёкшем/использованном коде. Ошибка `429` после пятой неверной попытки; для разблокировки нужен новый код после cooldown. API имеет IP-based throttling `30/hour` для проверки OTP.

**Важно:** реальные OTP не раскрываются ни в ответе, ни в HTML-странице; просматривать их в серверном журнале разрешено только на локальном стенде. Не отправляйте публичные логи, содержащие OTP, третьим лицам.

### Получить профиль

```http
GET /api/profile/
Authorization: Token f67d...
```

```json
{
  "phone_number":"+79991234567",
  "invite_code":"X2K9BZ",
  "activated_invite_code":null,
  "invited_phones":["+79990000002","+79990000003"]
}
```

Без токена: `401 Unauthorized`.

### Активировать чужой инвайт-код

```http
POST /api/profile/activate-invite/
Authorization: Token f67d...
Content-Type: application/json

{"invite_code":"AB12CD"}
```

Ответ `200 OK`: обновлённый объект профиля с `activated_invite_code: "AB12CD"`. При неизвестном, собственном или повторно активируемом коде: `400 Bad Request` с поясняющим полем `detail`. Регистр букв не важен.

### Завершить API-сессию

```http
POST /api/auth/logout/
Authorization: Token f67d...
```

Ответ `204 No Content`. Текущий токен удаляется. При следующем входе выдаётся новый токен.

## 5. Postman

Импортируйте `postman/TB4.postman_collection.json`. Коллекция включает пять API-запросов, переменные `base_url`, `phone_number`, `sms_code`, `token`, `invite_code`, и проверки статусов. После успешного подтверждения OTP сохраняет токен и собственный invite-code. **Перед запросом подтверждения вручную вставьте код из журнала сервера в переменную `sms_code`.** Для тестирования приглашения получите код другого пользователя, вставьте его в `invite_code`, а затем выполните «Активировать код» под своей учётной записью.

## 6. Архитектура

```text
tb4_referral_system/
├── accounts/
│   ├── migrations/                # начальная миграция моделей
│   ├── models.py                  # User, PhoneChallenge
│   ├── services.py                # бизнес-логика OTP и referrals
│   ├── forms.py                   # формы Django Templates
│   ├── views.py / urls.py         # HTML и маршруты
│   ├── templates/accounts/        # интерфейс
│   └── static/accounts/style.css
├── api/
│   ├── serializers.py             # валидация и ответы
│   ├── views.py                   # API-представления
│   └── urls.py
├── config/                      # настройки Django, URL, WSGI
├── tests/                       # API, сервисы и UI
├── postman/                     # коллекция Postman
├── Dockerfile
├── docker-compose.yml
└── README.md
```

**Модель данных:** `User(phone_number UNIQUE, invite_code UNIQUE, invited_by FK → User)`; `PhoneChallenge(phone_number UNIQUE, code_digest, expires_at, last_sent_at, attempts, consumed_at)`; штатная таблица DRF `authtoken_token`. OTP хранится в БД как **HMAC с серверным секретом**, а не в виде открытого кода. Шестисимвольный инвайт генерируется через `secrets` с обработкой коллизий на уровне уникального ограничения БД.

**Основной сценарий:**
1. Пользователь передаёт номер.
2. Бэкенд под блокировкой строки создаёт/обновляет OTP, проверяет частоту отправки, имитирует SMS.
3. Код сверяется HMAC-константным сравнением, увеличивается счётчик ошибок либо OTP помечается использованным.
4. При успешной проверке находится/создаётся пользователь, выдаётся DRF-токен.
5. В профиле пользователь активирует чужой код. Связь записывается атомарно и только один раз.

## 7. Тестирование

```bash
# локально, после pip install -r requirements-dev.txt
pytest

# через контейнеры (используется тестовая БД SQLite, PostgreSQL не затрагивается)
docker compose run --rm --user root web sh -c 'pip install -r requirements-dev.txt && pytest'

# статическая проверка стиля
ruff check .
```

`pytest.ini` использует `config.settings_test` и `pytest-cov` с порогом **75%** (`--cov-fail-under=75`). Тесты покрывают валидацию телефонов, OTP, срок действия и попытки, создание/повторный вход, активацию чужого инвайта, защиту профилей, веб-формы, CSRF-совместимую сессию и страницу схемы API.

> Статус первоначального релиза: исходники, тесты и конфигурация созданы; **полный тестовый прогон с Django не выполнялся в среде подготовки**, поскольку загрузка зависимостей была недоступна. Запусти `pytest` после установки зависимостей, чтобы подтвердить фактическое покрытие, а не полагаться на целевой порог в конфигурации. Для проверки блокировок и гонок также рекомендуется отдельное интеграционное тестирование на PostgreSQL.

## 8. Границы проекта и безопасность

- Демонстрационный SMS-бэкенд намеренно работает **только при DEBUG=1** и печатает OTP в логах. Для production требуется замена `send_simulated_sms` на интеграцию с SMS-провайдером, защищённое хранение секретов и HTTPS.
- DRF throttling на in-memory cache используется как вспомогательная защита **одного процесса**. В многопроцессорной среде необходим единый Redis/другой общий backend и внешний rate limiter. В БД дополнительно защищены повторная отправка одному номеру и попытки проверки.
- 4-значный OTP задан ТЗ; для реального продукта предпочтительнее более длинный код, контроль бюджета SMS и антифрод.
- Список приглашённых содержит полные номера по требованиям ТЗ, поэтому профиль доступен только авторизованному владельцу; реальный продукт может требовать маскирования и согласия субъектов данных.
- TokenAuthentication хранит постоянный токен до явного выхода. Для промышленной среды рекомендуется ротация токенов, мониторинг, HTTPS и более строгие механизмы восстановления сессии.
- Проверки активации используют транзакцию и `SELECT FOR UPDATE` на изменяемой строке пользователя. Для исключения конкурентных циклов при нескольких одновременных активациях нужны дополнительные транзакционные гарантии/блокировки; учебный проект не заявляет формально доказанную сериализуемость для произвольных цепочек.
- В качестве учебного стенда проект привязан к `127.0.0.1:8000`; значения по умолчанию для базы и секретов необходимо заменить перед публикацией.

## 10. Публикация в GitHub

Дипломное ТЗ требует удалённый репозиторий. Создай пустой репозиторий в своём GitHub, затем выполни из корневой директории проекта:

```bash
git init
git add .
git commit -m "TB4: referral system with phone OTP"
git branch -M main
git remote add origin https://github.com/YOUR_USERNAME/YOUR_REPO.git
git push -u origin main
```

`YOUR_USERNAME` и `YOUR_REPO` замени на фактические значения. **Не коммить `.env`**: файл уже исключён в `.gitignore`. После `git push` запустится подготовленная GitHub Actions workflow (`.github/workflows/ci.yml`) со статической проверкой, миграциями и pytest. Отдельная карта соответствия ТЗ — `ACCEPTANCE.md`.
